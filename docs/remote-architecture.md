# 远程协作架构

这篇文档回答三个问题：现在为什么只能小范围协作、远程要改什么、改完凭什么稳定。代码层面的字段与状态码见[远程协议 v1](remote-protocol.md)，部署见[远程部署](deployment-remote.md)。

## 一、结论先说

**能实现，而且不需要推翻现有同步内核。** 0.2 已经把最难的部分做对了：内容寻址（sha256）、每文件版本号、`If-Match` 乐观并发、三路文本合并、冲突副本落盘、崩溃后按 `intent/payload` 恢复。这些是远程协作里真正难写错的部分。

真正把协作范围锁死在"本机 / 同一台机器"的，是四行硬约束，加上一套为局域网设计的轮询模型：

| # | 位置 | 现状 | 远程后果 |
| --- | --- | --- | --- |
| 1 | `apps/collab-server/src/server.mjs:15-19`、`:73` | `assertLoopback()` 只允许 `127.0.0.1` / `::1` | 服务端**根本无法**监听公网或内网地址 |
| 2 | `server.mjs:115-121` | 带 `Origin` 的 WS 升级一律 403 | 浏览器/Web 端不可能接入（纯 VS Code 不受影响） |
| 3 | `snapshot-store.mjs:20-23` | `PRAGMA locking_mode = EXCLUSIVE` | 单进程独占数据库：无法滚动重启、无法多节点，重启即全员断线且无优雅停机 |
| 4 | `project-sync.ts:9`，`:658-698` | 每 650 ms 拉一次**全量**清单再逐文件核对 | 跨城 RTT 下空转开销与延迟同时放大（下方有实测） |

注意 1 和 2 是**产品决策**（早期只做本地验证），不是技术债；但 3 和 4 是真债：即使把 server 挪到公网，轮询模型在弱网下依然会"能用但难用"。

## 二、实测：轮询模型到底贵在哪

本机回环、单个 1 个文件的工作区，`node scripts/bench-remote.mjs --self --seconds 20`（同进程、同链路，只换传输方式）：

| 模式 | HTTP 请求 | 请求/小时 | WS 帧 | 变化可见 p50 | p95 | max |
| --- | --- | --- | --- | --- | --- | --- |
| 650 ms 全量轮询（0.2） | 31 / 20 s | 5 580 | 0 | 287 ms | 630 ms | 630 ms |
| WS 推送 + seq 增量（0.3） | 0 | **0** | 18（心跳 + 事件） | **14 ms** | 122 ms | 122 ms |

三点读数：

1. **空转成本：5 580 → 0 请求/小时。** 轮询每 650 ms 拉整份清单，文件越多单次响应越大；4096 个文件时单次约 300 KB 量级，一天约 1.6 GB/客户端。推送模式无变更就零请求，只有每 25 s 一帧心跳。
2. **延迟下限：287 ms → 14 ms（本机）。** 轮询把"多久发现变化"钉死在半个周期上；推送变成"落盘 → 事件单程"，与周期无关。跨城时轮询还要叠加 RTT，推送只付一个单程。
3. **推送只负责叫醒。** 事件不带文件内容，客户端收到后仍走"比 sha256 → 需要才下 blob"，所以推送挂掉不带来正确性风险，只是退化成 0.2 的行为。

> 测量口径：`latency` = 写入端**发起提交**到观察端**收到新版本**的耗时，含服务端落盘与广播。实测发现服务端是"先广播、后写完 HTTP 响应"，所以事件常早于提交方自己的响应到达——bench 的时间戳必须在发起请求**之前**登记，否则会测出 0 个样本（这个坑已在脚本注释里写明）。

## 三、远程稳定性 = 逐条消灭五种失效

远程不稳定从来不是"带宽不够"，而是五个具体失效模式。协议 v1 的每一节都对应其中一条，没有一条是装饰：

| 失效模式 | 症状 | 0.2 表现 | v1 机制 |
| --- | --- | --- | --- |
| NAT/防火墙掐空闲连接 | 静置几分钟后"连接还在但收不到东西" | 无长连接，靠轮询，感知为"延迟变大" | WS 心跳 `ping/pong`（25 s）+ 客户端 `2.5×` 静默看门狗主动判死重连 |
| 断线瞬间丢事件 | 重连后漏掉中间变化，或整轮全量重扫 | 全量清单重扫，文件多时卡顿 | 工作区级单调 `seq` + 客户端上报 `since` 续传；日志裁剪时下发 `reset` 强制全量 |
| 服务端重启/发版 | 全体成员同时卡死，且没有重连节奏控制 | 5 s 封顶指数退避后继续全量轮询 | 优雅停机广播 `reset` + close `1012`，客户端用 1 s 起的**短**退避快速回归 |
| 大文件 + 丢包 | 16 MiB 上传到 90% 失败，从头再来 | 整块 `PUT`，无分片无 Range | 分片上传（512 KiB、并发 3、按 `received[]` 乱序续传）+ 下载 `Range` 206，最后仍校验整文件 sha256 |
| 反复重连放大故障 | 网络抖动时几十个客户端同时重连，把服务打垮 | 指数退避封顶 5 s，无抖动 | `min(30s, 500ms×1.8^n) × (0.5~1.0)` 抖动、`hello` 复位、服务端回 `Retry-After` |

这五条是**远程稳定性的全部**。剩下的是权限与运维：成员级可吊销令牌、优雅停机、健康探针、单写者数据库。

## 四、目标架构

```text
VS Code 扩展（每台电脑）
  ├─ 本地磁盘（权威写入来源：VS Code 保存 / 外部工具）
  ├─ reconciler（保留 0.2 全部校验：sha256 + revision + 3-way 合并 + 冲突副本）
  └─ transport（新增）
       ├─ 能力协商  GET /v1/config           → 决定走推送还是降级
       ├─ 推送通道  WS /v1/events?since=seq   ← 服务端事件流 + 心跳
       ├─ 降级通道  GET /v1/workspace/changes?wait=25000（长轮询）
       ├─ 兜底轮询  650ms(回环) / 3000ms(远程)
       ├─ 提交      POST /v1/workspace/commit（If-Match + Idempotency-Key）
       └─ 大文件    POST /v1/upload → PUT 分片 → finish（断点续传）
                      ↕  公网 TLS（Caddy/Nginx 或服务端直连证书）
协作服务端（单进程 Node，SQLite WAL）
  ├─ HTTP/WS 入口（显式公网开关 LSW_BIND_PUBLIC=1 / TLS / 可信反代）
  ├─ 鉴权（共享令牌=owner，成员令牌 lsw1.<id>.<secret>，可吊销，角色 viewer/editor/owner）
  ├─ commit API（revision 乐观并发 + 幂等重放 10 min）
  ├─ seq 事件日志（workspace_seq / workspace_events，commit 与分配 seq 同一事务）
  ├─ 分片上传会话（落盘 <data>/uploads/<id>/*.part，30 min TTL）
  ├─ 推送 hub（WS 扇出 + 心跳 + ack 裁剪）
  └─ workspace 存储（沿用 0.2：路径 → revision/sha256/bytes）
```

关键设计取舍：

- **不用 CRDT/OT 重写。** 0.1 的单文件模式用 Yjs（CRDT）解决"同一段文字同时改"，代价是必须常驻 Y.Doc、体积线性增长、服务端要维护内存文档。工作区模式的目标是**按文件版本同步**，用"每文件 revision + 三路合并"就够，且天然支持二进制、支持外部工具写盘、支持离线任意时长后合并。远程化不需要换成 CRDT。
- **`seq` 与 `revision` 必须分离。** 0.2 只有 revision（文件级）。远程需要一个**工作区级时间轴**来表示"你漏了哪些事件"，这就是 seq。分离之后客户端可以只拉 delta，服务端可以裁剪日志，未来上多节点也只是把 seq 分配换到 Postgres/Redis。
- **推送只负责"叫醒"，不负责"传数据"。** 事件里只带 `path/revision/sha256/size`，客户端收到后仍走既有的"取清单行 → 比 sha256 → 需要才下 blob"路径。这样推送通道挂掉时，行为退化成 0.2，正确性不受影响。
- **幂等键 + 分片，是弱网下的两个必需项。** 没有幂等键，一次"提交成功但响应丢了"的重试会重复递增 revision，制造假冲突；没有分片，16 MiB 文件在 1% 丢包链路上成功率接近 0。

## 六、演进路线

| 版本 | 范围 | 判定标准 |
| --- | --- | --- |
| **0.3（本次）** | 显式公网绑定 + TLS/可信反代 + seq 事件日志 + WS 推送 + 长轮询降级 + 心跳/看门狗/抖动退避 + 分片续传 + Range + 成员令牌 + 优雅停机 | 两城各一台电脑，弱网模拟（`tc netem` 或 Clumsy）下：编辑后对端 < 300 ms 可见；断网 60 s 恢复无人工干预；服务端 `systemctl restart` 后 5 s 内恢复同步 |
| 0.4 | 成员管理 UI、在线状态（presence）、按文件的细粒度权限、审计日志 | 能回答"谁在什么时间改了哪个文件" |
| 1.0 | 多节点：seq 分配迁 Postgres/Redis，blob 迁对象存储，WS 节点用 Redis Pub/Sub 扇出 | 单节点故障不影响可用性；滚动升级零断连 |

**0.4 之前不做的事**（避免过度设计）：块级去重、P2P/WebRTC 直连、端到端加密、自研二进制协议。理由：当前规模（4096 文件 / 128 MiB / 十人量级）下这些的收益远小于复杂度成本，而 `seq` 抽象已经为它们留好了位置。

## 七、风险与已知限制

1. **SQLite 单写者仍是单点。** v1 的高可用边界是"进程重启 ≤ 10 s，客户端自动恢复"，不是"永不停机"。真正的多节点在 1.0。
2. **反代必须正确转发 WS。** Nginx 默认 `proxy_read_timeout 60s` 会掐掉长连接——这会表现为"每 60 s 重连一次"，看起来像客户端 bug，实际是代理配置。见部署文档的超时设置。
3. **事件日志裁剪窗口**（默认 4096 条/工作区，`LSW_EVENT_LOG_SIZE`）决定"断线多久后必须全量重扫"。十人日常写作够用；如果长期离线，客户端会拿到 `reset` 走全量，代价是一次全清单核对，不是数据丢失。
4. **文件数上限 4096、单文件 16 MiB、工作区 128 MiB** 未变。远程化不放大这些限制，只是让它们跨网可用。
5. 扩展仍需 VS Code 1.96+ 与 Node 24；服务端仍需单进程独占数据库文件。
